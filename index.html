Regula

Cum știi unde pui codul

N-am ales eu locurile. Proiectul ți le spune singur, prin trei indicii. Dacă le urmărești, la proba reală găsești fișierele fără să cauți prin toate folderele.

Indiciul 1

Comentariul // TODO

Profesorul a pregătit deja fiecare fișier și fiecare metodă. Acolo unde scrie // TODO trebuie să completezi tu. Nu creezi fișiere noi. În Android Studio le vezi pe toate în fereastra TODO (View → Tool Windows → TODO).

Indiciul 2

Importul din test

Fiecare test spune exact unde caută clasa. De exemplu, R2_ValidatorTest începe cu:

import ro.ase.dam.examen.domeniu.Validator;

Dacă muți sau redenumești clasa, testul nu mai compilează și pierzi toate punctele.

Indiciul 3

Doar în src/main

Task-ul zipPentruMoodle arhivează numai app/src/main. Orice ai scrie în src/test sau în altă parte nu ajunge la profesor.

package ro.ase.dam.examen.domeniu; ↓ în Java, punctele din numele pachetului devin foldere pe disc app/src/main/java/ro/ase/dam/examen/domeniu/Produs.java

De ce sunt împărțite în domeniu, json și xml

Fiecare pachet are o singură treabă, ca să nu ai tot codul amestecat într-un fișier uriaș:

  • domeniu conține ce este un produs (Produs) și regulile despre produse (Validator, ProduseService). Nu știe nimic despre JSON sau XML.
  • json și xml conțin cum citești produsele dintr-un anumit format. Dacă se schimbă formatul, modifici doar parserul, nu și Produs.
  • De ce nu în MainActivity? MainActivity e ecranul și are nevoie de telefon sau emulator. Testele rulează pe calculator, fără telefon, deci logica trebuie să stea în clase Java simple, care se pot testa separat.

Cerința 12p

Modelul: clasa Produs

app/src/main/java/ro/ase/dam/examen/domeniu/Produs.java
De ce aici
  • Testul R0_ModelTest o importă din ro.ase.dam.examen.domeniu.
  • Produs e „lucrul” cu care lucrează toată aplicația, deci stă în domeniu.
  • O rezolvi prima: toate celelalte cerințe creează sau citesc obiecte Produs.
Ce am scris, pas cu pas
  1. Trei câmpuri private: denumire, pret, stoc. Sunt private ca să nu le poată modifica nimeni direct (încapsulare).
  2. Constructorul copiază parametrii în câmpuri. this. e necesar pentru că parametrul are același nume ca și câmpul.
  3. Getteri, care citesc, și setteri, care modifică, pentru fiecare câmp.
  4. toString() întoarce un text cu toate valorile, de forma Produs{denumire='Paine', pret=5.0, stoc=10}.
public class Produs {

    private String denumire;
    private double pret;
    private int stoc;

    public Produs(String denumire, double pret, int stoc) {
        this.denumire = denumire;
        this.pret = pret;
        this.stoc = stoc;
    }

    public String getDenumire() {
        return denumire;
    }

    public void setDenumire(String denumire) {
        this.denumire = denumire;
    }

    // ... la fel getPret/setPret si getStoc/setStoc

    @Override
    public String toString() {
        return "Produs{" +
                "denumire='" + denumire + '\'' +
                ", pret=" + pret +
                ", stoc=" + stoc +
                '}';
    }
}
Capcane
  • Testul caută câmpurile după nume, prin reflection. Trebuie să se numească exact denumire, pret și stoc și să fie private.
  • Testul creează două produse diferite. Dacă salvezi valorile în câmpuri static, al doilea produs îl suprascrie pe primul.
Cerința 22p

Validarea: când e un produs valid

app/src/main/java/ro/ase/dam/examen/domeniu/Validator.java
De ce aici
  • Testul R2_ValidatorTest o importă din ro.ase.dam.examen.domeniu.Validator și apelează Validator.esteValid(p).
  • Validarea e o regulă despre produs, nu despre JSON sau XML. De aceea stă în domeniu, lângă Produs.
  • E o clasă separată, nu o metodă în Produs: o clasă se ocupă de un singur lucru. Clasa e final, are constructorul private și metoda static. Asta înseamnă că nu creezi obiecte Validator, ci apelezi direct Validator.esteValid(...).
  • Parserele nu folosesc Validator. Enunțul le cere doar să sară peste denumirile goale, iar validarea completă e o cerință separată, testată separat.
Ce am scris, pas cu pas (ordinea contează)
  1. Întâi p == null. Dacă ai apela p.getDenumire() pe un null, programul ar crăpa cu NullPointerException.
  2. Denumirea: e invalidă dacă e null sau goală. trim() taie spațiile de la capete, deci și " " e considerată goală.
  3. Prețul: trebuie să fie „strict pozitiv”, deci pret <= 0 e invalid. 0 nu e permis.
  4. Stocul: „nu poate fi negativ”, deci stoc >= 0 e valid. 0 e permis.
public static boolean esteValid(Produs p) {
    // un produs null nu e valid
    if (p == null) {
        return false;
    }
    // denumirea nu poate fi null sau goala (nici doar spatii)
    if (p.getDenumire() == null || p.getDenumire().trim().isEmpty()) {
        return false;
    }
    // pretul trebuie sa fie strict pozitiv
    if (p.getPret() <= 0) {
        return false;
    }
    // stocul nu poate fi negativ (0 e permis)
    return p.getStoc() >= 0;
}

Capcane
  • „Strict pozitiv” înseamnă > 0, iar „nu poate fi negativ” înseamnă >= 0. Citește cu atenție fiecare cuvânt din enunț.
  • Nu folosi isBlank(). Pe Android merge doar de la API 33, iar proiectul are minSdk = 24. trim().isEmpty() face același lucru și merge peste tot.
Cerința 32p

Importul JSON

app/src/main/java/ro/ase/dam/examen/json/ParserJson.java
De ce aici
  • Testul R3_ParserJsonTest o importă din ro.ase.dam.examen.json.ParserJson.
  • Pachetul json conține doar codul care știe formatul JSON. Produs nu știe nimic despre JSON.
Ce am scris, pas cu pas
  1. Creez o listă goală, în care adaug produsele.
  2. new JSONArray(text) transformă textul în vector.
  3. Parcurg vectorul cu un for și iau fiecare obiect cu getJSONObject(i).
  4. Citesc denumirea cu optString("denumire", ""), care întoarce "" dacă cheia lipsește. Dacă e goală, continue sare la următorul obiect.
  5. Citesc pret cu getDouble și stoc cu getInt, creez un Produs și îl adaug în listă.
public static List<Produs> dinText(String text) throws Exception {
    List<Produs> produse = new ArrayList<>();

    // textul este un vector JSON: [ {...}, {...}, ... ]
    JSONArray vector = new JSONArray(text);

    for (int i = 0; i < vector.length(); i++) {
        JSONObject obiect = vector.getJSONObject(i);

        String denumire = obiect.optString("denumire", "");
        // sarim inregistrarile cu denumirea goala
        if (denumire.trim().isEmpty()) {
            continue;
        }

        double pret = obiect.getDouble("pret");
        int stoc = obiect.getInt("stoc");

        produse.add(new Produs(denumire, pret, stoc));
    }

    return produse;
}

De ce org.json?

E biblioteca de JSON inclusă în Android. Testele rulează însă pe calculator, iar acolo clasele Android sunt doar niște „cutii goale” care întorc 0 sau null. De aceea profesorul a adăugat în app/build.gradle.kts linia testImplementation(libs.org.json), care aduce varianta reală și la testare. Linia asta e indiciul că trebuia folosit org.json.

Capcane
  • getString("denumire") aruncă excepție dacă cheia lipsește. optString(..., "") e mai sigur.
  • Întoarce lista goală, nu null, când vectorul e []. Testul verifică și cazul ăsta.
Cerința 42p

Importul XML

app/src/main/java/ro/ase/dam/examen/xml/ParserXml.java
De ce aici
  • Testul R3_ParserXmlTest o importă din ro.ase.dam.examen.xml.ParserXml.
  • La fel ca la JSON: pachetul xml conține doar codul care știe formatul XML.
Ce am scris, pas cu pas
  1. Construiesc un parser DOM cu DocumentBuilderFactory. DOM citește tot XML-ul și îl transformă într-un arbore de noduri.
  2. XML-ul vine ca String, nu ca fișier, deci îl dau parserului prin new InputSource(new StringReader(text)). Așa diacriticele din „Pâine” se citesc corect.
  3. getElementsByTagName("produs") îmi dă toate nodurile <produs>.
  4. Pentru fiecare, citesc <denumire>, <pret> și <stoc> cu metoda ajutătoare textCopil(), ca să nu scriu același cod de 3 ori.
  5. Sar peste produsele cu denumirea goală. Textul îl transform în numere cu Double.parseDouble și Integer.parseInt.
public static List<Produs> dinText(String text) throws Exception {
    List<Produs> produse = new ArrayList<>();

    // construim arborele DOM din textul XML
    DocumentBuilder builder = DocumentBuilderFactory.newInstance().newDocumentBuilder();
    Document document = builder.parse(new InputSource(new StringReader(text)));

    // luam toate nodurile <produs>
    NodeList noduri = document.getElementsByTagName("produs");

    for (int i = 0; i < noduri.getLength(); i++) {
        Element produs = (Element) noduri.item(i);

        String denumire = textCopil(produs, "denumire");
        // sarim inregistrarile cu denumirea goala
        if (denumire.isEmpty()) {
            continue;
        }

        double pret = Double.parseDouble(textCopil(produs, "pret"));
        int stoc = Integer.parseInt(textCopil(produs, "stoc"));

        produse.add(new Produs(denumire, pret, stoc));
    }

    return produse;
}

// textul din primul copil <tag> al elementului, fara spatii la capete ("" daca lipseste)
private static String textCopil(Element parinte, String tag) {
    NodeList lista = parinte.getElementsByTagName(tag);
    if (lista.getLength() == 0) {
        return "";
    }
    return lista.item(0).getTextContent().trim();
}

De ce DOM și nu XmlPullParser?

XmlPullParser vine din Android. În testele de pe calculator ar fi fost o „cutie goală”: Xml.newPullParser() întoarce null și testul crapă. Spre deosebire de JSON, aici profesorul nu a adăugat o bibliotecă de test. DOM (javax.xml.parsers) face parte din Java standard, deci merge și pe telefon, și în teste.

Dacă la proba reală ți se cere explicit XmlPullParser, folosește-l pe acela. Probabil profesorul va adăuga atunci și biblioteca de test potrivită.

Cerința 52p

Filtrarea produselor în stoc

app/src/main/java/ro/ase/dam/examen/domeniu/ProduseService.java
De ce aici
  • Testul R4_ServiceTest o importă din ro.ase.dam.examen.domeniu.ProduseService.
  • Un „service” conține operații pe produse (logica aplicației). Nu ține de JSON sau XML, deci stă în domeniu.
Ce am scris, pas cu pas
  1. Creez o listă nouă pentru rezultat. Pe cea primită nu o modific.
  2. Dacă sursa e null sau goală, întorc lista nouă, care e goală. Niciodată nu întorc null.
  3. Parcurg sursa și adaug în rezultat doar produsele cu getStoc() > 0. Sar peste elementele null, ca să nu crape.
public static List<Produs> filtreazaInStoc(List<Produs> sursa) {
    // lista noua: nu modificam lista primita
    List<Produs> rezultat = new ArrayList<>();

    // sursa null sau goala -> lista goala (nu null)
    if (sursa == null || sursa.isEmpty()) {
        return rezultat;
    }

    for (Produs p : sursa) {
        // pastram doar produsele cu stoc strict pozitiv
        if (p != null && p.getStoc() > 0) {
            rezultat.add(p);
        }
    }

    return rezultat;
}
Intră 
[A (stoc 5), B (stoc 0), C (stoc 3)]
Iese 
[A, C]   // B are stoc 0, nu e „în stoc”
Capcane
  • Testul șterge un element din lista sursă și verifică dacă rezultatul a rămas la fel. Dacă întorci aceeași listă sau o modifici cu sursa.removeIf(...), pierzi punctele.
  • Pentru null întorci lista goală, nu null.

La proba reală

Checklist pentru examen

  1. Citește ENUNT.md și notează-ți punctajul fiecărei cerințe. Începe cu cele care valorează mai mult sau sunt mai simple.
  2. Deschide fereastra TODO (View → Tool Windows → TODO) ca să vezi toate locurile în care trebuie să scrii.
  3. Rezolvă întâi modelul. Toate celelalte cerințe depind de el.
  4. Pentru fiecare cerință, citește întâi testul. Vezi exact ce valori intră și ce trebuie să iasă, inclusiv cazurile ciudate: null, listă goală, 0.
  5. Scrie codul în fișierul cu TODO. Nu muta fișierul, nu-l redenumi și nu schimba semnătura metodei: numele, parametrii și tipul întors rămân cum sunt.
  6. Rulează testele după fiecare cerință (.\gradlew test), nu doar la final. Așa știi imediat ce ai stricat.
  7. Predă: rulezi .\gradlew zipPentruMoodle și urci arhiva din moodle/.

Ce nu atingi niciodată

Testele din src/test, fișierele build.gradle.kts, folderul gradle/ și folderele generate (build/, .gradle/, .idea/).

Punctajul din teste e orientativ. Nota finală se stabilește și printr-o verificare manuală a codului, deci contează și ca soluția să fie scrisă curat, nu doar să treacă testele.
